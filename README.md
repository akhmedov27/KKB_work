# QMS Assistant KKB

Персональное локальное рабочее пространство менеджера СМК. Реализованы **QMS-001–QMS-003** по ТЗ версии 1.0 и согласованному перечню базовых функций. Это каркас, а не готовая медицинская или экспертная система. Используйте только синтетические тестовые данные.

## Запуск на Windows 10

Установите Python 3.12 или новее (с python.org, с опцией Add python.exe to PATH). Если нет прав администратора, используйте установку только для текущего пользователя, если это разрешено правилами организации. Откройте PowerShell в папке проекта:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

`Copy-Item` выполняйте только при отсутствии своего `.env`. Активировать окружение и менять ExecutionPolicy не требуется. Откройте **http://127.0.0.1:8000** в браузере. Остановить сервер: Ctrl+C. Если порт занят, используйте `--port 8001` и соответствующий адрес. Запускайте команды из корня проекта. Один процесс сервера достаточен для указанного оборудования.

Linux / облачная среда:

```sh
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

## Проверка

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

Откройте все пункты меню. Отправьте синтетический запрос в чат, обновите страницу и перезапустите сервер: история сохранится. В «Базе знаний» загрузите тестовый DOCX, XLSX или PDF. После загрузки обновите список по предложенной ссылке. Для проверки отказа загрузите TXT или файл больше лимита. `/health` проверяет доступность SQLite. В Linux: `.venv/bin/python -m pytest -q`.

## Что работает

- Восемь страниц навигации; русскоязычный адаптивный интерфейс, светлая/тёмная темы.
- Единый тестовый чат с явно обозначенным MockProvider. Пары запрос/ответ сохраняются в одной транзакции SQLite. История разделена на диалоги; на странице до 50 сообщений, более ранние доступны по ссылке.
- Локальная загрузка DOCX/XLSX/PDF, лимит по умолчанию 10 МиБ, отклонение пустых файлов. Потоковая запись с удалением частичного файла при отказе. Исходное имя, размер, дата и внутреннее имя сохраняются в SQLite. Внутреннее имя — случайный UUID, каталог загрузок не публикуется веб-сервером.
- Журнал операций и ошибок с ротацией; без текста запросов, содержимого файлов и секретов.
- Конфигурация через `.env` или переменные окружения. JavaScript, CSS и HTMX доступны локально, CDN при запуске не используется.

## Структура

```text
app/
  main.py          # маршруты FastAPI, обработка ошибок, сборка приложения
  config.py        # Pydantic Settings
  database.py      # соединения, внешние ключи, версия схемы и миграция
  history.py       # запросы и транзакции истории диалогов
  models.py        # SQLAlchemy: диалоги, сообщения и метаданные файлов
  providers.py     # AIProvider, MockProvider, недоступные Local/Cloud
  storage.py       # безопасное именование, лимит и запись загрузок
  templates/       # базовый макет, главная, страницы модулей, сообщения
  static/          # CSS, JS, локальный HTMX 2.0.4 и его MIT-лицензия
tests/test_app.py
requirements.txt
.env.example
.gitignore
```

## Конфигурация и данные

`QMS_DATA_DIR` — каталог данных (по умолчанию `data`, относительно текущей рабочей папки). `QMS_MAX_UPLOAD_MB` — целое число 1–100, размер в МиБ. `QMS_AI_PROVIDER` — `mock`, `local` или `cloud`. Только `mock` работает; другие значения провайдера возвращают 503 с объяснением, не подменяются тестовым ответом. Поля `QMS_LOCAL_MODEL`, `QMS_CLOUD_MODEL`, `QMS_CLOUD_ENDPOINT` зарезервированы: сетевые клиенты и чтение API-ключей не реализованы. Внешних ИИ-запросов нет при любой конфигурации.

Создаются `data/qms.sqlite3`, `data/uploads/`, `data/logs/app.log`. `.env`, данные и окружение исключены из Git. Файлы не извлекаются, не открываются сервером и не исполняются. Проверка расширения **не подтверждает формат и безопасность содержимого**, антивирус и парсеры не реализованы.

Резервная копия: остановите сервер и скопируйте **весь** каталог `data` в защищённое локальное место. Для восстановления при остановленном сервере верните каталог целиком. Не копируйте рабочую SQLite отдельно во время записи. Схема создаётся или обновляется при старте; перед переносом старой истории создаётся отдельная резервная копия SQLite (см. QMS-003 ниже).

## Границы этапа

База знаний (кроме приёма файлов), документы, инциденты, риски, аудиты, отчётность и редактирование настроек в браузере — явно подписанные заглушки. Нет поиска, извлечения текста, RAG, генерации документов, расчётов, реального ИИ, удаления данных, контроля версий, автоматического резервного копирования и отдельной ленты операций в интерфейсе (операции записываются в журнал). QMS-003 добавляет отдельные диалоги и миграцию старой истории. QMS-004 и дальнейшие этапы не начаты.

Это однопользовательский прототип без авторизации. Слушайте только `127.0.0.1`, не публикуйте в сети. Корпоративное внедрение требует отдельного согласования ИТ и ИБ. Docker, PostgreSQL, Qdrant и тяжёлые модели не используются. Зависимости обработки документов будут добавляться на соответствующих этапах.

Проверено в Linux с Python 3.12; команды Windows подготовлены, фактическая проверка на Windows 10 ещё требуется.


## QMS-002: интерфейс и навигация

Добавлены сворачиваемое меню для узких экранов (кнопка меню, закрытие Escape), обозначение текущей страницы, ссылка перехода к содержимому для клавиатуры и возврат на главную. Кнопка светлой/тёмной темы доступна на всех разрешениях; выбор сохраняется, если браузер разрешает локальное хранилище. При запрете хранилища тема работает до перехода на другую страницу.

На страницах модулей показаны назначение и реальные ограничения. Настройки отображают текущий провайдер и лимит файла без возможности менять серверную конфигурацию. Список файлов представлен таблицей с горизонтальной прокруткой на узком экране. Чат и загрузка показывают ожидание, ошибки и блокируют повторное нажатие кнопки во время запроса. После ошибки текст чата сохраняется для повторной отправки. Для неизвестного адреса в браузере есть русская страница 404.

### Обновление существующей копии на Windows

1. Остановите сервер: Ctrl+C в PowerShell.
2. Сделайте резервную копию каталога `data`.
3. Скачайте свежий ZIP ветки main из GitHub. Из распакованного проекта перенесите в вашу рабочую папку `app`, `tests`, `README.md` и `requirements.txt` с заменой файлов. Не заменяйте свои `.env`, `.venv` и `data`.
4. Запустите прежнюю команду Uvicorn. В браузере нажмите Ctrl+F5, чтобы обновить CSS и JavaScript.

### Необязательная браузерная проверка для разработчика

Для обычной работы приложения Playwright не требуется. Для повторения UI-проверки в тестовом окружении установите `playwright==1.62.0`, выполните `python -m playwright install chromium`. Запустите сервер с отдельным каталогом синтетических данных на порту 8002, затем `python tests/browser_smoke.py`. Параметр `QMS_TEST_URL` меняет адрес сервера, `QMS_CHROMIUM_PATH` позволяет использовать установленный Chromium. Скрипт отправляет тестовый запрос и сохраняет синтетический файл; не направляйте его на рабочие данные.


## QMS-003: база данных и история диалогов

На главной справа появилась «История диалогов». Введите название (до 120 символов), нажмите «Создать диалог» и отправьте тестовый запрос. Список позволяет переключаться между диалогами. URL содержит идентификатор выбранного диалога; обновление страницы сохраняет выбор. Главная без параметров открывает последний активный диалог.

- Сообщения имеют роль, дату и обязательную связь с диалогом. Внешние ключи SQLite включены на каждом подключении. Пара запрос/ответ и дата активности диалога сохраняются одной транзакцией: при ошибке записи не остаётся половины пары.
- История сообщений загружается по 50 записей, список диалогов — по 20. Ссылки «Более ранние сообщения» дают доступ ко всей переписке. На страницах ранней истории отправка отключена; для продолжения есть «К новым сообщениям».
- Даты отображаются в UTC. Сообщения в открытом чате добавляются сразу; список диалогов и ссылки страниц обновляются при обновлении страницы или по ссылке «Обновить историю».
- Удаление и переименование диалогов, поиск и экспорт истории не реализованы. Автоматического удаления сообщений нет. Для ИИ по-прежнему используется только MockProvider; история сама по себе не делает его настоящим ИИ.

### Сохранение данных при обновлении

Перед обновлением остановите сервер и скопируйте весь `data` в отдельное место. Обновите `app`, `tests` и `README.md` из свежего ZIP, сохранив свои `data`, `.env` и `.venv`. Новые зависимости не нужны. Не запускайте одновременно старый и новый сервер с одной базой.

При первом старте QMS-003:

1. Старая SQLite из QMS-001/QMS-002 проверяется и копируется средствами SQLite в `data/backups/qms-before-v1-<дата>-<идентификатор>.sqlite3`. Резервная копия проверяется через `integrity_check`. Если её создать не удалось, обновление не продолжается.
2. В одной транзакции создаются диалоги и переносится старая история в «История до QMS-003». Сохраняются идентификаторы, текст, роли и время сообщений, таблица метаданных документов и сами загруженные файлы. Если прежних сообщений нет, импортированный диалог будет пустым. В новой базе создаётся пустой «Первый диалог».
3. Устанавливается версия схемы `PRAGMA user_version=1`. Повторный запуск не дублирует историю и резервную копию. При ошибке миграции изменения схемы откатываются. Неизвестная старая схема или более новая версия БД останавливают запуск с объяснением.

Это резервная копия **базы перед миграцией**, а не периодическое резервное копирование всего хранилища: загруженные файлы в неё не входят. Полную копию `data` нужно сохранять отдельно. После миграции не запускайте старую версию приложения с новой базой. Для возврата к старой версии используйте заранее сделанную полную копию `data`, остановив сервер; записи, сделанные после копии, в ней отсутствуют.

### Самостоятельная приёмка

Создайте два диалога с разными названиями и запросами. Переключитесь между ними — сообщения не должны смешиваться. Обновите страницу и перезапустите сервер. Проверьте сохранность названий и сообщений. После обновления старой установки проверьте «История до QMS-003» и наличие файла в `data/backups`. Используйте только синтетические данные.

Автотесты: `python -m pytest -q` через Python из `.venv`. Дополнительные тесты находятся в `tests/test_history.py`: перенос старой базы и сохранность документов, откат миграции, отказ для более новой схемы, атомарная запись пары, защита внешних ключей, разделение диалогов, пагинация и повторный запуск.
